# PUR-6336 — Make improvements to catalog data schema flat files for Cycle d

**Type:** Task · **Project:** Purchase · **Status:** In Progress · **Parent:** AI Commerce Data Readiness & Evaluation Framework
**Use as:** ✏️ "is this even acceptance criteria?" — this is an implementation checklist, not outcomes.

## Description
Improve the catalog data schema flat files so AI evals can first find a product match, then dive into variants — for lower cost and better tool-call hints.

## "Acceptance Criteria" (as written — this is the problem)
1. Add a product-info section to the flat file to cut its size and let evals match a product first, then drill into variants.
2. Based on the APIs used before add-to-cart, identify needed tool calls, then recommend metadata to add at product/variant level so an app knows when to make those calls. (e.g. `isInventoried: true/false`; examples: time-based activities, voucher fencing, payment plans.) Document what you changed and why.
3. Ensure simple products without attribute combinations (ids: 438, 1944, 1181, 2125) also appear in the variants file.
4. Produce the "option 2" flat file (product-info section + new metadata + folded-in simple products) for the product list.
5. Produce the "option 3" flat file — same as option 2 but **excluding** ~19 metadata fields (activityType, skillLevel, durationMins, blackoutDates, payment-plan flags, cancellation fields, …) for the ~30 listed product ids.

## Why this is the teaching case
None of the above describes what "done and correct" looks like to someone *verifying* it — it's a list of tasks. Good practice prompt:

> *"Rewrite these as acceptance criteria: what would a reviewer check to confirm each is done right? Turn the tasks into testable outcomes."*
