# OpenSpec: The Product Requirements Process

> **Read this first.** This is the process Claude follows for turning a feature into specs and Jira tickets. It lives in the repo on purpose, so the agent reads it before writing anything. You do not need to edit it.

> **Command note:** This toolchain ships `/opsx:explore` and `/opsx:propose`. `/opsx:propose` generates the **proposal, the capability specs, the design doc, and the tasks together**: there is no separate `spec` or `design` command. The artifacts and who owns them are exactly as below.

## What OpenSpec Solves

AI coding tools go sideways not because the AI is bad, but because requirements only exist in chat history, so the AI fills every gap with a silent guess. OpenSpec gives those requirements a permanent home in the repo, in a structured format the AI reads before writing a line of code.

It also fixes a quieter problem: vague acceptance criteria let edge cases escape to QA and production. OpenSpec forces those decisions to be made, and written down, **before** engineering starts.

| Without OpenSpec | With OpenSpec |
|---|---|
| Requirements live in Jira descriptions and Slack threads | Every behavior is written down before coding starts |
| Engineers fill gaps with guesses, some right, some not | AI reads the spec, it doesn't guess |
| Edge cases surface in QA, not in planning | Edge cases caught in spec review, not QA |
| AI generates code that drifts from intent | Engineers ask better questions during planning |
| Corrections spiral and compound | QA validates against the spec, not intuition |
| No record of why decisions were made | Decisions are archived with the code that implements them |

## End-to-End Workflow

From idea to shipped code:

| Step | Who | Artifact | How |
|------|-----|----------|-----|
| 1 | PM (with Dev review) | **Exploration** | `/opsx:explore` |
| 2 | PM (with Dev review) | **Proposal** | `/opsx:propose` |
| 3 | **PM + QA + Dev** | **Spec** (one per capability) | review the `spec.md` files `/opsx:propose` generated |
| 4 | Engineer | **Design Doc** | review/refine the generated `design.md` |
| 5 | Engineer | **Tasks** | `/opsx:apply` works through `tasks.md` |
| 6 | Engineer | **Ship** | code |

> **The core rule:** No code is written until the spec exists. The spec is **not** a living document that gets updated mid-build to match what was built, it's a **decision record** that gets updated when a real decision changes. If an engineer discovers a constraint that invalidates a WHEN/THEN, the PM is notified and the spec is updated **before** QA, not after.

## The 5 Artifacts & Ownership

### 1. Exploration: *PM owns*

A free-form thinking session before any commitment. Run `/opsx:explore` to talk through a feature idea, the tool asks questions, surfaces tradeoffs, challenges assumptions, sketches the landscape. **Nothing is saved to the repo.** This is where "should we build X or Y?" gets resolved before it becomes someone's sprint work.

> **Guidance:** Treat Exploration as **required** for anything touching multiple user roles, a new integration, or significant edge cases. Optional for small, well-understood changes. A 20-minute Exploration prevents a week of rework.

### 2. Proposal: *PM owns*

The PM's primary deliverable. One sentence becomes a scoped, structured document with four sections:

- **Why**: the problem being solved
- **What Changes**: concrete outputs, not implementation steps
- **Capabilities**: named behaviors the feature introduces
- **Impact**: what the change touches

This replaces the vague Jira description. Generated by `/opsx:propose "one sentence description"`, then **reviewed and edited by the PM** before moving forward. *A wrong Proposal produces a wrong Spec.*

> **Example prompt:** *"A guest checkout flow, unauthenticated users can complete a lift ticket purchase, receive a confirmation email, and optionally create an account post-purchase."*

`openspec/changes/[feature-name]/proposal.md`

### 3. Spec: *PM + QA collaborate (and Dev too)*

One spec file per capability named in the Proposal. Each spec defines behaviors in **WHEN / THEN** format, explicit decisions that would otherwise live silently in someone's head or get guessed by the AI. This is where edge cases get written down, not discovered in QA.

**Why PM + QA together:** PMs know what the behavior *should* be; QA knows which edge cases will *break* it. A 30-minute spec review with QA before engineering starts catches more bugs than a 3-day QA cycle at the end. QA's role shifts from catching surprises to confirming the spec is complete.

> **Example:** WHEN an unauthenticated user completes checkout, THEN a confirmation email is sent within 60 seconds. WHEN the email matches an existing account, THEN the email prompts login, not account creation.

`openspec/changes/[feature]/specs/[capability]/spec.md`

### 4. Design Doc: *Engineer owns*

How the spec gets built, architecture, data models, component structure, risks, tradeoffs. Written by the engineer before any code. PMs don't need the internals, but should read the **risks** section and flag if any design decision contradicts the spec's intent.

`openspec/changes/[feature]/design.md`

### 5. Tasks: *Engineer owns*

A numbered checklist where each task maps to a design decision. This is what the AI works through with `/opsx:apply`, it reads the spec and executes against it rather than guessing. Tasks that don't trace back to a spec decision signal the spec is incomplete.

`openspec/changes/[feature]/tasks.md`

## Jira + OpenSpec: Recommended Split

Keep Jira for sprint tracking and stakeholder visibility. Use OpenSpec as the requirements/spec layer that lives in the repo. Jira answers *"what are we working on and when"*, OpenSpec answers *"exactly what should this do and why."* Collapsing them into one creates a mess in both directions.

| Jira owns | OpenSpec owns |
|---|---|
| Sprint board and backlog management | The Proposal (what and why) |
| Ticket status tracking (To Do → Done) | Capability specs with WHEN/THEN behaviors |
| Story points and velocity | Edge cases and explicit decisions |
| Release planning and roadmap | Design docs (how it gets built) |
| Bug tracking and severity | Tasks checklist (what the AI executes) |
| Stakeholder-facing progress reporting | Archived record of what shipped and why |
| Cross-squad dependency tracking | Source of truth for AI coding context |

### Where business value lives

This is the rule that makes "every ticket delivers value" real:

| Jira level | Maps to | Carries business value? |
|---|---|---|
| **Epic** | The Proposal (the whole feature) | Yes, the "Why" |
| **Story** | One **Capability** (an independently shippable behavior) | **Yes, this is the value-bearing bucket** |
| **Sub-task** | One item from `tasks.md` | No, pure work tracking |

A capability is named as a **behavior** a user can observe (`order-confirmation-routing`), so it has standalone value → it makes a legitimate Story. A "Frontend" or "Backend" ticket has no standalone value, that's the trap this rule exists to prevent.

## How Jira and OpenSpec Connect: Step by Step

1. **Create a Jira Epic for the feature.** The Epic is the planning artifact, it lives on the board, gets pointed, gets assigned. Its description can stay brief because the real requirements live in OpenSpec.
2. **Link the OpenSpec Proposal in the Epic.** One line: *"Full spec: [link to proposal.md]."* No wall of Jira text, no duplicated requirements that drift out of sync.
3. **Each Capability becomes a Story.** A Proposal with 3 capabilities = 3 Stories, each linked to its own `spec.md`. Natural, traceable decomposition, no arbitrary story-splitting at sprint planning.
4. **Each `tasks.md` item becomes a Sub-task** under its Story. Engineers move sub-tasks through statuses as they go; they don't duplicate task detail elsewhere.
5. **QA validates against `spec.md`, not the Jira description.** Acceptance criteria come from the spec QA helped write. A surprise in QA is a signal the spec was incomplete, not that QA missed something.

> **Traceability chain:** Jira Epic → OpenSpec Proposal → Capabilities → Jira Stories → `spec.md` → `design.md` → Sub-tasks → code

## How to Break a Project into OpenSpec Units

> **The sizing rule:** One OpenSpec change = one independently shippable unit of behavior. The right size: a Proposal you can describe in **1-2 sentences**, that produces **2-4 capabilities**, that an engineer can implement in **1-2 weeks**. If your Proposal needs a paragraph, it's two Proposals.

**Step 1, Explore the whole project first.** Before writing any Proposals, run `/opsx:explore` on the full scope. Surface all the capabilities the project touches, not to spec them yet, just to see the full landscape. This prevents Proposals that depend on other Proposals you haven't written.

**Step 2, Find the behavioral seams.** Split where **behavior changes independently**. Good seam signals: a different user role is involved, a different surface area is touched, or a piece could ship without the others and still deliver value. **Bad seam:** splitting by technical layer (frontend / backend), that's implementation, not behavior.

> **Example:** A "guest checkout" project splits into (1) guest cart + purchase flow, (2) confirmation email, (3) post-purchase account-creation prompt. Each can be specced, built, and QA'd independently.

**Step 3, Write one Proposal per seam, in dependency order.** If Proposal B depends on A, write A first and note the dependency in B's Impact section. Don't spec dependent features simultaneously, the downstream spec will have gaps only the upstream behavior can answer.

**Step 4, Let Capabilities define your Jira Stories.** Each capability named in the Proposal maps to one spec file and one Story. The Proposal does the decomposition work for you.

**Step 5, If a spec has more than 6-8 WHEN/THEN scenarios, split the capability.** A bloated spec means the capability is doing too much, usually two distinct behaviors got conflated. Rename and separate them. Smaller specs are easier to test and easier for the AI to implement correctly.

## Sizing Reference

🔴 **A Proposal is too big if…**
- "What Changes" has more than 6 bullets
- It touches more than 2 user roles
- It would take more than 2 weeks end-to-end
- Multiple engineers would work it simultaneously
- You can't describe it without "and also"

🟡 **A Proposal is well-scoped if…**
- Describable in one clear sentence
- 2-4 capabilities with clear behavior names
- One engineer can own it start to finish
- QA can test it independently
- Could ship to a subset of users behind a flag

## PM Writing Guide

### Writing the Proposal

- **Write the Why before the What.** The Why is the most important sentence, it tells the engineer what problem this solves so they make good micro-decisions. *"Users abandon checkout when forced to create an account"* beats *"business wants guest checkout."* Don't restate the feature name.
- **What Changes = outputs, not implementation steps.** List what will *exist* after this ships. *"A guest can complete checkout without an account"* is a change. *"Add a guest flag to the user model"* is a Design Doc detail.
- **Name Capabilities like behaviors, not components.** Good: `guest-session-persistence`, `order-confirmation-routing`. Bad: `checkout-component`, `user-model-update`. The name becomes the spec file name, and a Jira Story title a QA engineer who's never seen the code can read.
- **Review the generated Proposal carefully.** It will surface implicit decisions you made, scope, constraints, affected areas. Fix anything wrong *before* moving on. A wrong Proposal produces a wrong Spec, which produces wrong code.

### Writing WHEN/THEN Specs

- **WHEN = trigger. THEN = observable system response.** WHEN is a user action or system event; THEN is what the system does, specific, observable, testable. Precise enough that a QA engineer can write a test case from it with no follow-up questions.
  > WHEN a guest submits checkout with a valid card, THEN an order is created with status "pending" and a confirmation email is queued within 5 seconds.
- **Write the unhappy paths, they matter more than the happy path.** For every happy path, ask: what if the input is invalid? a downstream service fails? the user navigates away mid-flow? Each answer is a WHEN/THEN. If you don't write it, the AI guesses.
  > WHEN a guest submits checkout and the payment processor returns a timeout, THEN the order is NOT created, the cart is preserved, and the user sees a specific retry message, not a generic error.
- **Explicitly state what does NOT change.** Negative constraints prevent scope creep. If guest checkout should not affect loyalty points, write it down. Unwritten constraints get ignored, not out of negligence, but because no one can read your mind.
- **Run a 30-minute spec review with QA before handing to engineering.** QA's job here is to find missing *scenarios*, not missing code. This single habit is the highest-ROI process change available.

## Anti-Patterns to Avoid

- **✗ Writing the Proposal as a longer Jira description.** If you're copy-pasting from Jira into the Proposal, stop and run Exploration first. Jira describes intent; Proposals describe scope and behavior.
- **✗ WHEN/THEN scenarios that describe UI, not behavior.** *"WHEN the user clicks the blue button, THEN a modal appears"* is a UI description. Behavior specs survive redesigns; UI specs don't.
- **✗ Treating the spec as a one-way handoff.** If an engineer discovers a constraint that changes a WHEN/THEN, the PM needs to know and the spec updated **before** QA. A spec that doesn't reflect reality is worse than no spec.
- **✗ Skipping Exploration for complex features.** Technically optional, but for anything touching multiple roles, a new integration, or real edge cases, skipping it means your Proposal has gaps.
- **✗ Splitting Proposals by technical layer.** "Frontend Proposal" + "Backend Proposal" for one feature is the wrong decomposition. Split by independently shippable behavior, things different users can observe working.
